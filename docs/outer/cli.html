CLI shorthands

Run from the repo directory. Channel IDs live in channels.json (rewritten each boot; voice channel IDs under each guild's voice_channels). Quick tables first, full options under each.

The universal one (do.py)

python benham.py do list                    # every capability, grouped by tier
python benham.py do list --tier destructive # just one tier
python benham.py do help <action>           # one action's params, which are required, its tier
python benham.py do <action> key=value ...  # run it

do.py covers all 56 registered capabilities — one CLI for the whole registry, because the old one-file-per-action pattern meant a new capability was three edits and usually got only two (which is how purge went so long with no CLI at all). Values parse as JSON when they look like it, so fields='[{...}]' works.

Destructive actions are two calls. First returns a dry-run with real counts and a token; second passes confirm_token= to fire exactly what was previewed. The token is bound to the parameters captured at preview time — editing the arguments between the calls invalidates it rather than silently running something else.

python benham.py do purge_messages channel_id=8093…8612 limit=20 contains="test"
#   --- DRY RUN, nothing has happened ---
#   Delete 1 messages from #asd in Testing Server
#   ...repeat with: confirm_token=80ac01
python benham.py do purge_messages channel_id=8093…8612 limit=20 contains="test" confirm_token=80ac01

Everyday shortcuts

commanddoes
send.py <channel_id> "msg"send
draft.py <channel_id> "msg"review-first send
dm.py <user_id>|--tyler "msg"DM someone
delete.py <channel_id> <message_id>delete one message — permanent
fetch.py <channel_id> [limit]history → result file
catchup.py <channel_id> [limit]invisible read, one channel
read_history.py [limit|all]invisible read, every non-Testing guild

send.py

Args: <channel_id> then the message — everything after the id is joined into one text, so quotes are only needed to protect shell characters. Writes an atomic request into outbox/; the running bot delivers within ~2s and files the request + result pair under outbox/sent/ (or failed/).

python benham.py send 8093…8612 "world's up at UnknownCaz-Gt25.exaroton.me"

draft.py

Args: <target_channel_id> "reply text". Posts a clearly-labeled DRAFT into Testing #asd for your eyeball, and prints the exact send.py command that delivers it for real. Nothing reaches the target channel until you run that printed command yourself — the human-in-the-loop is the point.

python benham.py draft 1491…0261 "yo xavier, sounds good"
# → DRAFT lands in Testing #asd; it prints:
#   python benham.py send 1491…0261 "yo xavier, sounds good"

dm.py

Args: <user_id> "text", or --tyler "text" as the owner shorthand. Discord only lets a bot DM someone who shares a guild with it and hasn't disabled member DMs — when that fails, the request lands in outbox/failed/ with a Forbidden error rather than failing silently.

python benham.py dm --tyler "backup finished, all green"
python benham.py dm 2739…5952 "hey"

delete.py

Args: <channel_id> <message_id>. Deletes ONE specific message. Benham's own messages always work; someone else's needs Manage Messages. Deletion is permanent. For bulk delete-by-filter use do.py purge_messages (which gets the dry-run + confirm gate).

python benham.py delete 8093…8612 1531…4876

fetch.py

Args: <channel_id> [limit], default 20. Pulls the last N messages via the running bot into outbox/sent/<name>_result.json. For live messages, tail inbox.jsonl instead.

python benham.py fetch 8093…8612 50

catchup.py

Args: <channel_id> [limit], default 40. Run with -u for unbuffered output. Logs in as Benham with an invisible presence (no green dot), prints the last N messages oldest→newest, exits. The process contains no send / react / reply code at all, so it cannot post or trigger anything. Intended for a light read — recent activity and vibe, not deep profiles.

python -u benham.py catchup 1525…9072 15     # what's happening in #minecraft-chat

read_history.py

Args: [limit] per channel, default 100 — or all / full / 0 for everything. Same invisible client as catchup, but sweeps every readable text channel in every guild except Testing (always excluded).

python -u benham.py read_history            # 100 per channel, all friend guilds
python -u benham.py read_history all        # no limit

Voice

commanddoes
speak.py <vc_id> "text"join, speak, leave
listen.py <vc_id>join and transcribe
stoplisten.py <vc_id>stop and leave

speak.py

Args: <voice_channel_id> "text". Joins, speaks via an edge-tts neural voice, disconnects. The voice is switchable by the named "B-voice" roster in voices.json.

python benham.py speak 8097…7301 "dinner's ready, get off the server"

listen.py / stoplisten.py

Args: <voice_channel_id> each. Listen joins and transcribes utterances with faster-whisper into voice_transcript.jsonl; wake words ("benham"/"claude") are flagged in the record. Autonomous replies to wake words only happen with BENHAM_AUTO_REPLY=1, and only in auto_reply_guilds. Stoplisten makes it leave.

python benham.py listen 8097…7301
python benham.py stoplisten 8097…7301

Exaroton, in Discord rather than the terminal: /server status|start|stop|restart <server> — per-guild gating in exaroton_watch.json (Testing = all servers, operator required; Chillbar = Isle of Berk, anyone). The watchdog posts crash/offline alerts for watch: true servers.

Webhooks — posting without the bot

A different animal from everything above: webhook.py posts straight to Discord's webhook API from a saved URL in webhooks.json (gitignored — the URLs are secrets). No bot involved — no gateway, no token, works while benham/bot.py is stopped, and the post appears under the webhook's own name/avatar, not Benham's. It reaches channels Benham was never invited to (the reason it exists: the Isle of Berk changelog).

python benham.py webhook "hello world"                # default webhook
python benham.py webhook -t test "hello"              # a named one
python benham.py webhook --title "Deploy done" "v1.2 is live" --color 3066993   # rich embed
python benham.py webhook --username "AlertBot" "..."  # override displayed name
python benham.py webhook --list                       # configured webhooks (never prints URLs)

Full options

optiondoes
message (positional, optional)the text to post — or the embed description when --title is used. Omitting both message and --title = "Nothing to send", exit 2.
-t / --target <name>which named webhook from webhooks.json; omitted = the config's "default". Unknown name = error listing what IS configured.
--url <url>post to a raw webhook URL, bypassing the config entirely
--username <name>override the displayed sender name for this one post (no avatar override exists)
--title <text>switches to a rich embed: title = this, description = the message. Without it you get a plain content post — the two modes are exclusive.
--color <int>embed color as a decimal int (3066993 = green). Only meaningful with --title.
--listprint configured webhooks (name, server, channel, note — never the URLs) and exit

webhooks.json shape

{
  "default": "test",                  // used when --target is omitted
  "webhooks": {
    "test": {
      "url": "https://discord.com/api/webhooks/<id>/<token>",   // the secret
      "server": "Testing Server",     // human label only
      "channel": "#asd",              // human label only
      "note": "freeform reminder"
    }
  }
}

Add a webhook = add another named entry. The file is gitignored because the URL is the credential — anyone holding it can post.

Exit codes

0 delivered (Discord answers HTTP 204) · 1 Discord refused (prints the HTTP status + body) · 2 nothing to send.

Caution: this path lives outside the chokepoint — no policy gates, and a webhook post writes no log line anywhere. Why that trade was made: Inner → Webhook identity.

status.py

No args. Answers "is Benham up and what is it doing" without touching Discord: running benham/bot.py pid, guilds/channels seen (from channels.json), AUTO_REPLY state + allowlist, last login / command-sync lines from the newest log. Never prints tokens.

python benham.py status

usage.py

flagscope
(none)the newest log
--log <file>a specific log
--allevery *.out / bot.log together — full history
--todayonly today's lines

Reports three things: process cost (memory, CPU seconds, uptime), API cost (tokens per path and the cache hit rate — whether the ~7.4k-token static prefix reads from cache dominates a message's price), and activity (which capabilities ran, what policy refused, what got proposed and confirmed). Dollar figures are list-rate estimates and the output says so — PC sessions actually bill the plan, not per-token.

python benham.py usage --today

watch_pc.py

flagdoes
(none)follow the active session live
--lastreplay the most recent session and exit
--listlist recent sessions

Reads the full JSONL transcript Claude Code already writes per session (under ~/.claude/projects/<encoded-cwd>/) — nothing was added to the bot to make this observable; the record existed and just had no reader. Strictly read-only: it cannot affect a running session, so watching is always safe mid-task.

What needs the bot running

Everything that rides the outbox queue needs the bot up: send, draft, dm, delete, fetch, do.py actions, and all three voice commands.

Standalone — work with the bot down: webhook.py, status.py, catchup.py, read_history.py, usage.py, watch_pc.py, guest.py. The invisible readers log in briefly as Benham with an invisible presence — no green dot, and the process contains no send/react/reply code at all, so it cannot post or trigger anything.
