CLI shorthands

Run from the repo directory. Channel IDs live in channels.json (rewritten each boot; voice channel IDs under each guild's voice_channels). Quick tables first, full options under each.

The universal one (do.py)

python benham.py do list                    # every capability, grouped by tier
python benham.py do list --tier destructive # just one tier
python benham.py do help <action>           # one action's params, which are required, its tier
python benham.py do <action> key=value ...  # run it

benham.py do covers all 56 registered capabilities — one CLI for the whole registry, because the old one-file-per-action pattern meant a new capability was three edits and usually got only two (which is how purge went so long with no CLI at all). Values parse as JSON when they look like it, so fields='[{...}]' works.

Destructive actions are two calls. First returns a dry-run with real counts and a token; second passes confirm_token= to fire exactly what was previewed. The token is bound to the parameters captured at preview time — editing the arguments between the calls invalidates it rather than silently running something else.

python benham.py do purge_messages channel_id=8093…8612 limit=20 contains="test"
#   --- DRY RUN, nothing has happened ---
#   Delete 1 messages from #asd in Testing Server
#   ...repeat with: confirm_token=80ac01
python benham.py do purge_messages channel_id=8093…8612 limit=20 contains="test" confirm_token=80ac01

benham.py send

Args: <channel_id> then the message — everything after the id is joined into one text, so quotes are only needed to protect shell characters. Writes an atomic request into outbox/; the running bot delivers within ~2s and files the request + result pair under outbox/sent/ (or failed/).

python benham.py send 8093…8612 "world's up at UnknownCaz-Gt25.exaroton.me"

benham.py draft

Args: <target_channel_id> "reply text". Posts a clearly-labeled DRAFT into Testing #asd for your eyeball, and prints the exact benham.py send command that delivers it for real. Nothing reaches the target channel until you run that printed command yourself — the human-in-the-loop is the point.

python benham.py draft 1491…0261 "yo xavier, sounds good"
# → DRAFT lands in Testing #asd; it prints:
#   python benham.py send 1491…0261 "yo xavier, sounds good"

benham.py dm

Args: <user_id> "text", or --tyler "text" as the owner shorthand. Discord only lets a bot DM someone who shares a guild with it and hasn't disabled member DMs — when that fails, the request lands in outbox/failed/ with a Forbidden error rather than failing silently.

python benham.py dm --tyler "backup finished, all green"
python benham.py dm 2739…5952 "hey"

benham.py delete and benham.py purge

Args: <channel_id> <message_id> for delete; <channel_id> [--days N] [--limit N] for purge. Benham's own messages always work; someone else's needs Manage Messages. Deletion is permanent.

Two steps since 2026-08-26. Both were legacy outbox verbs that reached msg.delete() / ch.purge() with no allowlist, no dry-run and no confirmation — the tier-3 guarantee was a property of the verb name, not of the effect. They now enqueue the registry twins (delete_message, purge_messages), so the first call previews and returns a token and you re-run with --confirm-token. A preview-only call exits non-zero, because nothing was deleted. --scope guild is gone: the gated twin is per-channel, and a whole-guild sweep needs its own tier-3 capability rather than a flag. For author/text filters use benham.py do purge_messages.

python benham.py delete 8093…8612 1531…4876
#   ...prints the preview and a confirm_token, deletes nothing
python benham.py delete 8093…8612 1531…4876 --confirm-token 80ac01

benham.py fetch

Args: <channel_id> [limit], default 20. Pulls the last N messages via the running bot into outbox/sent/<name>_result.json. For live messages, tail inbox.jsonl instead.

python benham.py fetch 8093…8612 50

benham.py catchup

Args: <channel_id> [limit], default 40. Run with -u for unbuffered output. Logs in as Benham with an invisible presence (no green dot), prints the last N messages oldest→newest, exits. The process contains no send / react / reply code at all, so it cannot post or trigger anything. Intended for a light read — recent activity and vibe, not deep profiles.

python -u benham.py catchup 1525…9072 15     # what's happening in #minecraft-chat

benham.py read_history

Args: [limit] per channel, default 100 — or all / full / 0 for everything. Same invisible client as catchup, but sweeps every readable text channel in every guild except Testing (always excluded).

python -u benham.py read_history            # 100 per channel, all friend guilds
python -u benham.py read_history all        # no limit

Conversations — ask, and close the loop

Stage 3's surface. A conversation is an ask with a counterparty, a deadline and a state, and it outlives the session that opened it — so a task can ask you something, exit, and a later session reads your answer. See the Inner page for why it works that way.

commanddoes
ask --queueWhat is already waiting on you, plus any answers nobody collected. Read this before asking.
ask "question"Ask Tyler from a running session and wait. --no-wait to fire and read later.
conv listEverything still open. --all includes closed and banked.
conv show c7One conversation with its full event log.
conv close c7 "outcome"Shut the loop. --tell also DMs them the outcome.
conv bank c7 "reason"Give up waiting, keep the question.

Joining the queue

Several sessions can be waiting on you at once. They arrive as one numbered DM, and you answer by number — in any order, including all of them in a single message. See the Inner page for the slot rules that make that safe.

flagdoes
--queuePrint the line and exit. Prints uncollected answers first.
--priority blocking|normal|wheneverWhere the session puts itself. Default normal.
--why "…"One line on why it placed itself there. Shown to you next to the question.
--purpose "…"What the answer is for. Defaults to the question.
--project "…"Which project it is about.
--timeout 900Seconds this process waits. Default 900 — one nudge cycle.
--no-waitSend it and exit. The answer waits in the store.
python benham.py ask --queue                       # ALWAYS first
python benham.py ask "sqlite or json?" \
    --priority blocking --why "cannot pick a schema without this"
python benham.py ask "ready to deploy?" --no-wait

The priority is the session's own claim, and you see every one of them. That is the design, not an oversight: a session that has read the queue is ranking itself against visible claims rather than in a vacuum, which is where inflation comes from. Nothing stops one claiming blocking, and nothing hides it — a blocking question is marked ⚠️ blocking a session in your DM, a whenever one is marked (no rush), unmarked means normal, and whatever it said in --why is printed underneath. Within a level it is strictly first-come-first-served, so the only way past someone is to claim a higher level, in writing, where you can see it.

ask prints the queue on every call, but by then the priority is already on the command line — which is what --queue is for. A session that has not looked first is guessing.

A timeout is not a failure. Only that process stopped watching — the bot keeps nudging on its own schedule, and your answer is recorded whenever it arrives. A session that dies mid-wait loses the asker, never the question.

Uncollected answers are printed first, above the queue. An answer you have already given is worth more than a question about to be asked, and the commonest way to waste your time is a fresh session re-asking something you answered to a session that has since exited. Act on it, then conv close <id> "what happened".

An outcome is required. close refuses without one, because a silent close is the exact failure this was built to end — work that looks finished from the inside and reads as silence from the outside.

Closing and telling stay two facts even behind one flag. --tell queues a message the running bot delivers, and the counterparty-told event is only written when Discord actually accepts it. So a failed delivery can never look like a shut loop — check with conv show.

In conv list, the arrow is the direction: -> is something we asked them, <- is something they told us and we owe an answer to.

Webhooks — posting without the bot

A different animal from everything above: benham.py webhook posts straight to Discord's webhook API from a saved URL in webhooks.json (gitignored — the URLs are secrets). No bot involved — no gateway, no token, works while benham/bot.py is stopped, and the post appears under the webhook's own name/avatar, not Benham's. It reaches channels Benham was never invited to (the reason it exists: the Isle of Berk changelog).

python benham.py webhook "hello world"                # default webhook
python benham.py webhook -t test "hello"              # a named one
python benham.py webhook --title "Deploy done" "v1.2 is live" --color 3066993   # rich embed
python benham.py webhook --username "AlertBot" "..."  # override displayed name
python benham.py webhook --list                       # configured webhooks (never prints URLs)

Full options

optiondoes
message (positional, optional)the text to post — or the embed description when --title is used. Omitting both message and --title = "Nothing to send", exit 2.
-t / --target <name>which named webhook from webhooks.json; omitted = the config's "default". Unknown name = error listing what IS configured.
--url <url>post to a raw webhook URL, bypassing the config entirely
--username <name>override the displayed sender name for this one post (no avatar override exists)
--title <text>switches to a rich embed: title = this, description = the message. Without it you get a plain content post — the two modes are exclusive.
--color <int>embed color as a decimal int (3066993 = green). Only meaningful with --title.
--listprint configured webhooks (name, server, channel, note — never the URLs) and exit

webhooks.json shape

{
  "default": "test",                  // used when --target is omitted
  "webhooks": {
    "test": {
      "url": "https://discord.com/api/webhooks/<id>/<token>",   // the secret
      "server": "Testing Server",     // human label only
      "channel": "#asd",              // human label only
      "note": "freeform reminder"
    }
  }
}

Add a webhook = add another named entry. The file is gitignored because the URL is the credential — anyone holding it can post.

Exit codes

0 delivered (Discord answers HTTP 204) · 1 Discord refused (prints the HTTP status + body) · 2 nothing to send.

Caution: this path lives outside the chokepoint — no policy gates, and a webhook post writes no log line anywhere. Why that trade was made: Inner → Webhook identity.

benham.py status

No args. Answers "is Benham up and what is it doing" without touching Discord: running benham/bot.py pid, guilds/channels seen (from channels.json) state + allowlist, last login / command-sync lines from the newest log. Never prints tokens.

python benham.py status

benham.py usage

flagscope
(none)the newest log
--log <file>a specific log
--allevery *.out / bot.log together — full history
--todayonly today's lines

Reports three things: process cost (memory, CPU seconds, uptime), API cost (tokens per path and the cache hit rate — whether the ~7.4k-token static prefix reads from cache dominates a message's price), and activity (which capabilities ran, what policy refused, what got proposed and confirmed). Dollar figures are list-rate estimates and the output says so — PC sessions actually bill the plan, not per-token.

python benham.py usage --today

What needs the bot running

Everything that rides the outbox queue needs the bot up: send, draft, dm, delete, fetch, and do actions.

Standalone — work with the bot down: webhook, status, catchup, read_history, usage, watch_pc, guest, ideas, conv. The invisible readers log in briefly as Benham with an invisible presence — no green dot, and the process contains no send/react/reply code at all, so it cannot post or trigger anything.
