Config reference

One file runs the control plane: control.json. Everything here assumes you know the three rules.

The rules

  1. Restart after ANY edit. The file is read once at import. This cuts both ways — adding a guest and removing one both wait for the next boot. One answer to "who may talk to Benham" beats a live-reload race.
  2. Missing config = most-restrictive defaults, always. A deleted key never opens something up.
  3. control.json.example documents every key in its _comment twins — it's the reference the table below summarizes. No secrets in either file; tokens live in environ.env (gitignored).

Most-restrictive defaults

The philosophy, stated once: a typo can only turn things off. Missing keys fall to the most restrictive value. The guest grant machinery survives its own feature and still grants nothing: a name in config does nothing unless code ALSO flags that capability for guests, and nothing does. test_policy asserts the guest column of the capability matrix is empty, so a regression shows up as a failing test rather than as silence. Privileged intents default off because requesting an ungranted intent bricks login on the next restart — the failure mode of "off" is two capabilities that plainly say why they're unavailable, which beats a bot that won't start. Unrecognised guest modes disable guest chat rather than guessing.
