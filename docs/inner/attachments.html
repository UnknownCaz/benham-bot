Attachments

Files come in through quarantine and go out through a preview that names them. Nothing is ever run.

What it does

Looking, with no tool call at all (2026-08-18): a message's own images now reach the model as picture blocks before the first API call, on both DM surfaces, along with a quoted reply, a forwarded message and a link preview's text. A screenshot plus "what's wrong here?" is answered in one call rather than two, and it works whether or not the model thinks to reach for a tool — which on the guest path it could never do anyway. benham/core/msgparts.py encodes; bot.inbound_content assembles. Four formats (png, jpg, gif, webp), 4 per message, 4MB each; anything outside that is named with its reason rather than dropped. It taints the turn — that is the security half, and the reason it is not simply free.

Reading: read_attachments channel_id= message_id= downloads what one named message carries into downloads/<message_id>/ (gitignored — and NOT your Windows Downloads), returns name/size/type per file, inlines text up to 20k chars. save=false looks without keeping; max_bytes= raises the 8MB default. Sending: send_file / dm_user take path=/paths=; Discord's 10-file / 25MB limits are checked locally so a failure names the file instead of arriving as a bare 413.

Why we chose this

Reading is tier 0 because three properties make a mistaken call cost nothing — and the tier only holds while all three do:

  1. No URL parameter. It fetches what a named message carries. A general "download this URL" tool would be aimed by whatever text Benham last read — the exact shape the injection defences refuse. (The archived guest workspace copied this rule too: imports came from a message the guest authored, or not at all.)
  2. Bytes land only under downloads/, under a rewritten name. The uploader controls the filename and nothing else — ..\..\Windows\System32\evil.dll is a legal name for a Discord upload, and CON.txt is a device, not a file. Rewrites are reported, not silent; a final realpath check refuses anything still resolving outside the folder. (This hygiene lives in pathsafe.py. It was extracted to be shared with the guest workspace — one implementation of "may this path exist" rather than two drifting copies — and outlived it: the workspace was archived on 2026-08-16, this path is the only caller left, and the extraction is still the right shape for the next one.)
  3. Nothing is ever run. Windows-runnable extensions are flagged executable: true and written anyway — a blocklist would refuse ordinary work (.jar mod files) while preventing nothing, since the file is only ever bytes on disk. The archived guest workspace took the stricter rule — refusal — because a guest had no legitimate reason to author .bat onto your disk. No guest path writes files at all now, so the only live rule is the flag-and-write one above.

Outbound is where the gate sits: send_file is outward + posts — in a tainted turn the confirmation preview names the files, which is the only reason approving it means anything. Everything read is taints-marked and wrapped in untrusted-data markers before the model sees it: a crash log someone uploaded is information to report, not instructions to follow.

Paper trail

Downloaded files sit in downloads/<message_id>/; each read_attachments result (rewrites reported, executable flags) is in its outbox/sent/…_result.json; sends log like any outward action.
