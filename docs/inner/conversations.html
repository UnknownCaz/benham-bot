Conversations

An ask with a counterparty, a deadline and a state — which outlives the session that opened it. The session that asks may be gone by the time the answer arrives; the thing that closes the loop reads a file, not a variable in someone's memory.

Why it exists

Benham is built on actions: fifty-odd stateless verbs you invoke and forget. That is the right shape for purge_messages. It is the wrong shape for "ask Doom whether the fix worked", which has a counterparty, a purpose, a deadline, and an answer that arrives minutes later in a different process.

Every loop that used to stall was one of those with nowhere to live:

The problemAs a conversation
Doom files a bug and never hears backa conversation with no close
A session needs Tyler and cannot reach hima conversation with no target
Notifications with no priorityconversation urgency, unmodelled

It also fixes the trust defect by construction. Benham once insisted it had never run a pc_task while Tyler was looking at the approval prompts it had just sent, because its only record was a corrupted turn list. A conversation object is a record: state, history, log. "What did I do?" stops being a memory question and becomes a lookup.

The invariants

Each of these is enforced in conversations.py rather than documented and hoped for.

InvariantWhy it is code, not a convention
An answer names its questionThe one that pays for everything else. Until 2026-08-17 it was spelled "one live ask per person" — with a single candidate, binding could not be wrong. Asks queue now, so the slot carries that weight instead.
A defer only ever extendsAn away signal is information about when to ask again, not permission to ask sooner. Capped at one hour.
A close carries an outcomeA silent close is the exact bug this exists to end — work that looks finished from the inside and reads as silence from the outside.
Telling is not closingTwo separate events, so a failed DM can never look like a shut loop.
Banking keeps the questionGiving up waiting is not deleting, and it is not refusing to hear. The question stays readable, and for ten minutes after the bank it still accepts an answer.

A bank is not a door slamming (Tyler's call, 2026-08-17). c11 banked at 08:10:28 and he answered it at 08:11:43 — 75 seconds late. The answer went nowhere, silently, and Benham then told him it had been recorded. Giving up waiting and refusing to hear are different things and only the first was ever meant: banking preserves the question precisely because it is still a real question, so throwing away a real answer to it is strictly worse than any alternative. Past the window the refusal is loud rather than silent — the tool says the conversation banked, when, and that nothing has been recorded. ANSWERED and CLOSED are shut for a different reason and no window reopens them: those already have an answer, and quietly replacing one is the silent misfiling slots exist to prevent.

This page said "one live ask per person" for a day after that stopped being true. It is recorded here rather than quietly corrected, because the failure is the recurring one in this project: a confident claim with nothing checking it. The rule was real, it was load-bearing, and replacing it was deliberate — but a reader who trusted this page would have believed a safety property the code no longer had.

Direction — who owes whom

A conversation has a counterparty, but the obligation can run either way, and almost every rule depends on which.

directionmeaningrules
ASKINGwe asked them something; we are waitingnudges apply; several may be live, and they queue
OWEDthey told us something (a bug, an idea) and we owe an outcomenever nudged, never queued

Nudging someone about a bug they reported is chasing them for an answer we owe them, which is why OWED is never nudged. It is excluded from the queue for a sharper reason: if a report counted as waiting-on-its-author, his next message would be a candidate answer to his own bug report. Doom filed three reports in two days — every one of them would have been sitting in his line.

The queue — several sessions, one message

Sessions cannot see each other and never will. Before 2026-08-17 the second one to need Tyler was simply refused, because one live ask per person was what made an answer bindable. Tyler's call was to let them queue and replace the guarantee rather than drop it.

Every ASKING conversation waiting on one person forms a line, and it is delivered as one numbered DM rather than N separate ones:

3 things waiting on you. Answer any of them by number - "2: sqlite" -
or just reply and I'll work it out.

1. restart prod? ⚠️ blocking a session
     deploy is wedged
2. sqlite or json?
3. drop the cache? (no rush)

Priority is self-assessed, and that is deliberate

Tyler's design, over a recommendation to derive it from whether the session was blocked — and he was right. Inflation is what happens when you rank yourself in a vacuum, where "important" is the only safe answer. The queue is the one place unrelated sessions can meet, so a session that reads it first (ask --queue) is ranking comparatively — and claiming blocking next to two existing blockings is visibly worthless. Nothing enforces looking first; the shared file is what makes looking useful.

levelthe claim it makes
blockingthis session cannot continue without an answer
normalit gates something, but there is other work meanwhile
wheneverno rush; answer it when convenient

Named rather than numeric because there is always a bigger integer, and an arms race is the failure mode. These three are a claim about the asker's own state — something a session actually knows, and something Tyler can sanity-check at a glance.

It is advisory but recorded: nothing stops a session claiming the top, and nothing hides it either. The level and the reason it gave both appear next to the question. Line-jumping costs visibility rather than being impossible. Within a level the order is strictly first-come-first-served, so the only way past someone is to claim a higher level — which shows up in the queue and in Tyler's message.

The slot is the binding handle

The number is not decoration. It is what replaced the one-live-ask rule: "2: sqlite" names its question exactly, with no model involved. Two properties keep that true.

Slots are recomputed, never stored. A stored slot would go stale the moment anything ahead of it was answered, and a stale number is worse than no number — it binds an answer to the wrong question silently.

They are recomputed against the screen, not against the live queue. This is the half that was missing until 2026-08-18, and the bug it caused is worth spelling out because the fix looks like the thing it fixes:

on screen:   1. which database?   2. drop the cache?   3. ready to deploy?
he answers   "1: sqlite"        → live queue is now [drop, deploy]
he answers   "2: yeah drop it"  → live slot 2 is READY TO DEPLOY

Nothing re-renders the message when he answers, so the list he can still read renumbers underneath him. shown_queue() resolves against the ids the message actually displayed, so 2 keeps meaning the second thing he can see. A slot whose question has since been answered resolves to nothing rather than to its neighbour, and falls through to the model — which then has to say how it read the message.

Edited in place, replaced when it matters

One message, kept current, so the numbering a reply refers to is the numbering on screen. The catch that shapes the whole design: a Discord edit fires no notification.

what happenedwhat the message doeswhy
a question joins the backedited in place, silentlynothing at the top changed; a fresh ping for a low-priority addition is noise
a question lands at the frontthe old message is deleted and a new one sentit must arrive visibly — a blocking claim delivered silently is the opposite of what claiming it is for

The stale message is deleted rather than left above the new one, so 3 cannot mean two different things depending on how far he scrolls.

The front-of-line rule used to require a queue longer than one, on the assumption that a lone question had no message to edit yet. It does: the batch id is never cleared when a queue empties, so the first question after a quiet spell found the old message, took the edit path, and arrived with no notification at all. The one case most likely to be urgent was the one guaranteed to be silent. Caught by writing the test the delivery path never had — the stub could not be edited or fetched, so every attempt threw into a bare except and fell through to sending. It looked tested and was not.

Answers nobody collected

A session that asks with --no-wait, or that simply exits before he replies, leaves the answer sitting in the store with nothing to deliver it to. ANSWERED-but-not-CLOSED already meant exactly "an answer arrived and nobody acted on it", so this needed no new state — only a surface. ask --queue prints them first, above the questions, because an answer already given is worth more than a question about to be asked, and the commonest way to waste his time is to re-ask something he has already answered to a session that has since exited.

The beats

Code owns timing; the model owns meaning. Nothing in conversations.py asks a model anything, which is what lets a loop close with no session running.

beatwhen
askfirst delivery. Does not spend a nudge, and restarts the countdown from delivery — a conversation opened while the bot is down must not burn its fifteen minutes before anyone sees it. One batch message delivers every question it displays, so all of them are marked and all of their clocks start together.
waitingalready on their screen, deadline not reached. Nothing is sent. Not every call arrives from the tick loop — ask fires one the instant a conversation is opened, in order to deliver it — so "the next beat" cannot mean "a nudge, whenever you ask".
nudge15 minutes later, twice at most. Quotes the question verbatim; a nudge that rephrases reads as a second, different question.
bankbudget spent. The owner is told a collaborator went quiet — unless the owner is the one who went quiet, in which case a third message saying so is noise.

A background loop in bot.py ticks this every 60 seconds against the 15-minute policy. It decides nothing: due() reads the clock and the budget and says nudge-or-bank; the loop only delivers.

Delivery is a fact about a question, not about a message, and until 2026-08-17 it was neither — it was inferred from ask_message_ids, which is the binding record. The batch message id lands on every question the message shows, because a reply to it may answer any of them. So when three sessions asked within 300ms, whichever delivery job ran first stamped the other two, their own jobs concluded the question had already gone out, and they sent a nudge — one second after the question first appeared. Two of the three burned a nudge on a question nobody had had time to read, hit the two-nudge cap early, and banked about fifteen minutes before they should have. Tyler answered one of them 75 seconds after it banked; the answer had nowhere to go. Two facts were sharing one field and the quieter one lost.

Binding — how a reply attaches to a question

Tyler's rule, and the asymmetry is the point:

routecertaintyrecorded as
He types the number — "2: sqlite"certain, resolved against the message on his screenbound_by="slot"
A Discord reply to the ask (or to a nudge)certain — while that message names one questionbound_by="reply"
Anything elsethe model judges, and must say so in the same breathbound_by="judged"

Requiring a reply every time is friction; letting the model silently decide is how an instruction gets swallowed as an answer. Judging and announcing keeps the fast path fast while making a wrong guess visible. The record stores which route was taken, so the three are never confused later.

A reply stops being certain once the message lists several questions. Replying to a batch of three says "one of these" without saying which, so it hands off to the model rather than attaching to whatever happens to be at the front — which is precisely the failure the old one-live-ask rule existed to prevent.

Answering several at once works, because a numbered list invites exactly that. Tyler broke the first version within minutes of it shipping by doing the obvious thing — answering all three in one numbered message, which is literally what the message asks for. A greedy pattern bound slot 1 to the whole message, so one question swallowed the answers to the other two and both went on being nudged for things he had already answered. Both layers had failed, and the second is the instructive one: the model read all three correctly and recorded none of them, because nothing had told it it could bind more than one. Slot markers are now cut at line starts only — a "2." mid-sentence is prose, and the parse has to fail toward "this is not a list" rather than toward finding structure that is not there.

Read-only triage

A filed report can be investigated by a real Claude Code session restricted to Read/Glob/Grep — a non-read tool is denied outright rather than asked about. That guarantee does double duty: a stranger's bug report cannot reach a write, and it cannot make Tyler's phone buzz either. Triage that pesters him is triage he turns off.

That was why triage_conversation was not behind blocked_when_tainted while pc_task was: the taint wall existed because pc_task could write, and triage could not. Both left with the PC lane in Phase B (2026-09-05, INTENT decision 39) - a report is still recorded on its conversation; investigating it is a session Tyler starts at the keyboard.

A diagnosis is stored on the conversation and the state stays open. "We think it is X" is not something anyone should be told is resolved.

Driving it

See CLI shorthands. In short: ask --queue to read the line before joining it, ask from a running session, conv list / show to read, conv close … --tell to shut the loop and say so.

Where this goes next

Deliberately not built here. Tyler, 2026-08-17: "i think this idea is its own monster so lets start with the ask queue with the expectations this will grow into a later form." The later form is a session-to-session channel — sessions reading and replying to each other rather than only reading a queue: deferring, merging duplicate questions, handing off work. The shape he has in mind is rooms, not a flat channel: "a shared group chat for sessions with rooms for each, kinda like a discord server for active claude sessions that could need to communicate."

The queue is about coordinating questions to Tyler; that is about sessions coordinating with each other, which is a different system with its own failure modes — loops, deadlock, sessions talking each other out of asking at all. Conflating them would have dragged the queue down. The queue is already the degenerate case of it: one room, one member, and every message a question. Whatever gets built should be able to look at the queue and see itself.
