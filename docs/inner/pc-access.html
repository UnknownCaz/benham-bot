PC access

A real Claude Code session on the actual machine — read freely, ask before changing.

What it does

codesession.py drives the real Claude Code CLI through the agent SDK, with your own settings and skills loaded — "restart Isle of Berk" works because your exaroton skill is there, not because this repo knows what exaroton is. Reached via the pc.. DM prefix or the pc_task capability.

Rooms (2026-08-18, INTENT item 22). The pc.. prefix now routes through spawn_in_room: behaviour is unchanged, but every task lands in the standing scratch room with author, timestamp, and the session id — which is the resume handle. pc.. continue: <task> resumes the scratch worker with its context intact; a named room's worker resumes by default (a room is a thread), and past the handoff bound a continue rolls over to a fresh session that is told the room holds the thread. A spawned session gets a pointer to its room, never room content — it reads the room itself via the CLI, so other writers' text never sits in the instruction seat. Sessions post nothing anywhere by themselves: v1 rooms are pull-only, and the only automatic write is the session's own final message, posted into its room as the report. pc_task remains registered during the transition.

Why we chose this

The allowlist is of reads, not writes. Anything unrecognised is treated as a change and asks. When a future Claude Code version adds a tool this file has never heard of, the failure mode is an unnecessary question — not an unreviewed write. Fail closed, in the direction that merely annoys.

The full command, because an approval you can't read isn't one. An early version truncated the approval DM to 80 characters — which would have meant approving commands you couldn't actually see. 1200 now.

The workdir is not a sandbox, and secrets are readable — on purpose. Benhams-inbox/ is a starting point; the session can go anywhere. Reads are free, so anyone who can DM Benham could ask it to read environ.env. The chosen defence is not a block but a trail: every read of a credential-shaped path logs loud as SECRET-READ. Two honest reasons: full file access is the feature being bought, and the DM door is already owner-only — the log exists for the day that assumption fails. Hardening to a flat deny is a one-line change to _SECRET_RE's use, documented in the code for exactly that day.

Tightest origins in the registry. {OWNER_DM, LOCAL_CLI} + blocked_when_tainted: reachable only from a direct DM or the local shell, and not at all once the turn has read what other people wrote — see The taint model for why that's a flat deny, not a confirm.

Paper trail

Every session writes a full JSONL transcript (Claude Code's own, under ~/.claude/projects/<encoded-cwd>/) — python benham.py watch_pc follows it live; nothing was added to the bot to make this observable, the record existed and just had no reader. Approval requests appear as DMs and as bot-log lines; credential-path reads flag SECRET-READ. Billing per task shows in benham.py usage (estimates; sessions currently bill the subscription).
