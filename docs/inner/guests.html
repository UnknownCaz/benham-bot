The guest system

The one exception to "Benham obeys one person" — and the most security-sensitive thing in the codebase, which is why it's built out of absences.

What it does

Whitelisted friends can DM Claude-through-Benham: a plain conversation plus server-side web search, capped daily, separate memory, separate persona. They can also file ideas and bug reports with an idea.. prefix, which are quarantined and tracked as conversations they are told the outcome of. Admin procedures live in Outer → Guest admin.

Since 2026-08-18 they can also be understood. An image a guest sends arrives as a picture the model actually looks at, and so do a replied-to message, a forwarded message and a link preview's text — see Attachments. Before that, guest.py built its API call out of plain text, so an attachment did not arrive degraded: it never arrived at all, and the model was not told one existed. It filled the gap the way models do, telling the one project participant to try uploading it again. He did. Twice. A file it cannot open now gets a fixed, free reply rather than silence or a spent message, and images are not charged extra against the daily cap — a web search costs double because it is a second round trip; an image is only a bigger first one.

A tool loop used to sit beside this — a file workspace, allowlisted channel reads and Anthropic-side code execution, built across seven commits in August 2026. It was archived on 2026-08-16 because the usage never came: fifteen code runs, every one on the two days it was built; three workspace files; no recorded use of shared reads. The one genuine attempt to use code execution failed, because the sandbox has no network. See archive/guest-tools/. The grant machinery it needed is still in place and still grants nothing, which the boot banner asserts out loud.

Why we chose this

The founding property is an absence, not a rule. guest.py calls the API with no client tools argument — not an empty list, not a filtered one. So "can a guest reach capability X" has the same answer for every one of them, for restart, and for anything added next year, without that code knowing what a capability is. A gate that has to enumerate what it forbids can be out of date; this one can't be.

Inlined images do not touch that property, and the reason is worth stating plainly — it is the one place the absence looks like it might have been bent. The content blocks are finished before the call, assembled in bot.py from the message that was just sent in, by code the model never talks to. No tool definition, no name for a model to emit, no tool-result loop to steer. A guest gains the ability to be looked at; they do not gain the ability to make Benham fetch. The question above — "can a guest reach capability X" — has exactly the answer it had before, for the same reason, and the distinction that matters is whether the model can aim it. It cannot.

Everything is denied at least twice, independently. rule_guest refuses any capability not named in guest.capabilities — and nothing is ever named there — while GUEST_DM's absence from DEFAULT_ORIGINS makes rule_origin_allowed refuse it again.

Corrected 2026-08-17. This paragraph used to name rule_owner as one of the two denials, on the grounds that GUEST_DM is in Origin.HUMAN. rule_owner explicitly steps aside for guests (if ctx.origin in Origin.GUEST: return None) and leaves them to rule_guest. The error was copied out of a comment in policy.py that carried the same mistake; that comment was corrected the same day, and this page had reproduced it before anyone noticed. Two independent denials is still true — they are just not the two that were named.

A capability written next year inherits both without anyone remembering guests exist — invariant 1 of the refactor: new capabilities are guest-proof the day they're written.

The grant model needs three declarations to agree: the registry flag (guest=True — code says what's possible), the origins set (must name GUEST_DM), and guest.capabilities in control.json (config says what's on). A config typo can only ever disable; it can never expose an action the code didn't mark. And the registry refuses at import to register guest=True on anything outward, posting, destructive, confirmable, or taint-blocked — a violating declaration crashes the boot rather than existing as a lie.

All three are currently empty, and that is the point. Since the tool loop was archived on 2026-08-16 the registry declares guest=True on nothing, no config carries guest.capabilities, and the guest chat path passes no client tools at all — so even a granted capability would have no caller. The machinery is kept armed around an empty room deliberately: it is what makes the next capability someone writes guest-proof on the day it is written, rather than on the day someone remembers to check.

Separate modules, not flags. guest.py keeps its no-tools property forever; agent.py stays yours. "The same loop but a smaller list" is one wrong conditional from being the same list — two files that do different things cannot be collapsed by accident. That argument was tested in August 2026 when a refactor plan proposed merging them, and it won: the loops stayed apart and only the six lines they genuinely shared (storing a turn pair, in turnmemory.py) were extracted. Merging would have traded a property the code has for one a conditional claims.

Guests never see a confirmation — anything that would ask you is a flat no for them (the preview would leak what would happen; the traffic would aim approval fatigue at you). Guest turns are born tainted. Nothing a guest does executes on your machine. When code execution existed it ran on Anthropic's servers, never here; a local sandbox was rejected as a research project with a catastrophic failure mode.

The threat model, stated plainly: a hostile guest can burn caps and log ugly searches — nothing else. They cannot take any outward action, cannot reach a confirmation, and cannot run anything on your PC. test_policy asserts this exhaustively rather than leaving it to argument: every capability against every origin, with the guest column required to be empty. A capability appearing there is a security regression, not a test to update.

Paper trail

guest_usage.json (daily counters), guest_searches.jsonl (every query, hand-moderable), guest_memory.json (their conversations — a separate file so a typo can't merge a guest thread with yours). guest_work/ ARCHIVED belonged to the tool loop and nothing writes it now; guest_runs.jsonl ARCHIVED was planned for the same feature and never shipped.
