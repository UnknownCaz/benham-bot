The guest system

The one exception to "Benham obeys one person" — and the most security-sensitive thing in the codebase, which is why it's built out of absences.

What it does

Whitelisted friends can DM Claude-through-Benham. Chat mode (today's default): a plain conversation plus server-side web search, capped daily, separate memory, separate persona. The staged refactor adds, behind flags: a file workspace CODE SHIPPED (grants empty), allowlisted channel reads PLANNED, and Anthropic-server-side code runs PLANNED. Admin procedures live in Outer → Guest admin.

Why we chose this

The founding property is an absence, not a rule. guest.py calls the API with no client tools argument — not an empty list, not a filtered one. So "can a guest reach capability X" has the same answer for all 56, for pc_task, and for anything added next year, without that code knowing what a capability is. A gate that has to enumerate what it forbids can be out of date; this one can't be.

Everything is denied at least twice, independently. GUEST_DM is in Origin.HUMAN, so rule_owner refuses it; it's also absent from DEFAULT_ORIGINS, so rule_origin_allowed refuses it again. A capability written next year inherits both without anyone remembering guests exist — invariant 1 of the refactor: new capabilities are guest-proof the day they're written.

The grant model needs three declarations to agree: the registry flag (guest=True — code says what's possible), the origins set (must name GUEST_DM), and guest.capabilities in control.json (config says what's on). A config typo can only ever disable; it can never expose an action the code didn't mark. And the registry refuses at import to register guest=True on anything outward, posting, destructive, confirmable, or taint-blocked — a violating declaration crashes the boot rather than existing as a lie.

Three modules, not flags. guest.py (chat) keeps its no-tools property forever; guest_agent.py (workspace) runs a loop over exactly the granted set; agent.py stays yours. "The same loop but a smaller list" is one wrong conditional from being the same list — two files that do different things cannot be collapsed by accident.

Guests never see a confirmation — anything that would ask you is a flat no for them (the preview would leak what would happen; the traffic would aim approval fatigue at you). Guest turns are born tainted. Nothing a guest does executes on your machine, at any stage — code runs, when they come, are Anthropic-side only; a local sandbox was rejected as a research project with a catastrophic failure mode.

The threat model is re-answered per stage: a hostile guest today can burn caps and log ugly searches — nothing else. With the workspace: fill a capped folder with inert bytes (runnable suffixes refused however a file arrives). With shared reads: see exactly what you chose to publish to every guest. Never: any outward action, any confirmation, any code on your PC.

Paper trail

guest_usage.json (daily counters), guest_searches.jsonl (every query, hand-moderable), guest_memory.json (their conversations — a separate file so a typo can't merge a guest thread with yours), guest_work/ (their files, once granted), guest_runs.jsonl PLANNED (Stage 6). Samples: Outer → Guest admin.
