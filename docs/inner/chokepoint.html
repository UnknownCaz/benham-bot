The chokepoint

One process talks to Discord. One function decides what's allowed. Everything else is files.

What it does

benham/bot.py is the single persistent process holding the Discord connection. Nothing else talks to Discord directly — the CLI scripts drop atomic request files into state/outbox/, the bot polls every ~2s, executes, and files a result:

CLI (benham.py send|draft|do …)  →  state/outbox/*.json
                                          |
                    the bot polls the outbox every ~2s
                                          |
      Discord  ←→  the bot  →  state/outbox/sent|failed/*_result.json
                       |
 every message seen → state/inbox.jsonl    each boot → state/channels.json

The second chokepoint is logical: capabilities.run() is the single execution path for all 64 capabilities — authorize → validate → authorize_target → confirm-or-execute — and policy.py is the single place authorization is decided. Every entry point must state its origin (OWNER_DM, OWNER_GUILD, OWNER_VOICE, LOCAL_CLI, SYSTEM, GUEST_DM); a call with no context or an unrecognised origin is denied.

Why we chose this

The file bus: it keeps the heavy always-on process separate from one-shot actions, and it makes every action leave a request/result pair on disk whether or not anyone remembered to log — the audit trail exists by construction, not by discipline. One token, one gateway also prevents the duplicate-reply problem the supervisor separately guards against.

The policy chokepoint exists because of a specific bug. identity.agent_allowed() encoded "the owner cannot drive the agent from Chillbar", was asserted by a passing test — and was dead code. bot.on_message re-implemented a subset inline and left the guild check out. Green suite, opposite behaviour. A gate that is written but not wired is indistinguishable, from tests, from one that works. The design goal is narrow: make that shape impossible. One decision point, mandatory origin declaration, and deny-on-unknown means a new call site threaded wrong fails loudly instead of permitting silently.

Two phases on purpose: authorize() answers caller rules with no network access at all — a refusal never resolves a channel and never reports anything about one. authorize_target() runs after parameter validation, because "may this touch that guild" isn't answerable before then. Refusals leak nothing.

Two things deliberately live outside the chokepoint — benham.py webhook and the exaroton watchdog. What that trade costs: Webhook identity.

Paper trail

inbox.jsonl — everything seen; outbox/sent|failed/ — every action as a request/result pair (samples: Daily driving); channels.json — the world map, rewritten each boot; policy refusals log in the bot log naming the rule that fired.
