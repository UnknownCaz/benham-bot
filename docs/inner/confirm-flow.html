Confirmation flow

Three independent gates in front of every destructive action — and the model can never open the last one itself.

What it does

  1. Guild allowlist. destructive_guilds in control.json. Tier-3 anywhere else is refused outright — checked before the dry-run, so a refused action never even reports what it would have touched.
  2. Mandatory dry-run. The first call performs nothing and returns real facts: counts, date spans, author breakdowns, who currently holds the role. This is what catches a wrong channel id or an older_than_days off by 10×.
  3. Explicit confirm, and on tier 3 the token is required. In a DM: preview + a token, then an affirmative. On tiers 1–2 a bare "yes" fires. On tier 3 it does not — a typed reply has to carry the 6-hex token (yes a1b2c3), and naming the action is no longer enough. The Approve button is unaffected: it holds the token already, so the ordinary path is still one tap. From the CLI: re-run with confirm_token=, which has always been mandatory there.

Changed 2026-08-24, and the history matters. This page originally claimed only an affirmative naming the token fires. That was false when it was written — the token was always optional, and a bare "yes" fired anything parked, on every tier. An audit caught the false claim; Tyler's 2026-08-17 answer was not to make the token mandatory but to require that the yes name what it is confirming. On 2026-08-24 he went the rest of the way — "one copy-paste action is worth an irreversible action" — because the naming rule's guarantee is word overlap with ordinary English, over a word set built from channel, user and role names: a purge parked on #general could be fired by "yeah, general seems right", and that set silently grows with every capability added. A token is exact and does not rot. Governed by confirm.require_token_tier3 (default on); set it false to fall back to the naming rule.

Tiers 1–2 still take a bare "yes". What stops a stray "yeah" three messages later there:

  • A whitelist, not a guess. read_reply() matches the phrase against a fixed affirmative set with any token removed, and returns None for anything it does not recognise. A None is treated as no action — ambiguity is never consent.
  • One at a time. Parking a new confirmation supersedes the old one rather than queueing it, so "yes" is never ambiguous between two destructive actions — which is the case that would actually hurt.
  • A short clock. The window is ten minutes on the DM path (below), not an hour, so the interval in which a bare "yes" can hit anything is small.

On tier 3 all of that still applies, and the token requirement sits on top of it. The refusal is spoken, not silent: an affirmative arriving without the token is told what is missing and handed the exact string to send, because an unexplained no-op on a destructive action is answered by saying yes again, louder. A mistyped or lapsed token is answered out loud for the same reason — that is the one new way to fail here, and it happens to someone who did exactly what they were asked. Cancelling never got harder — a bare "no" still works on every tier, so the safe direction stays the convenient one.

The refusal is deliberately no wider than the set that used to fire. A sentence that merely opens with "yes" and names nothing ("yes, you're totally right") still falls through to the agent as ordinary conversation: over a confirm window that can run an hour, that is far likelier to be talk than consent, and nagging it would make the gate something to route around.

Previews expire: expired = cancelled, silence is never assent. The TTL depends on which path parked it — confirm.conversation_ttl_seconds (600 = 10 min) for the DM flow, confirm.ttl_seconds (3600 = 1h) for everything else, per _ttl_for(). The agent parks with origin "dm", so ten minutes is the number you actually live with; confirm.describe prints the real one. The token is bound to the parameters captured at preview time — editing the arguments between the two calls invalidates it rather than silently running something else.

Benham cannot successfully tell you a preview is waiting when none is. Added 2026-08-17, after it did exactly that twice in one evening — "preview should be waiting on your end", then "preview should be up now" — with no tool call behind either. Neither has a PROPOSED line in the log, and Tyler spent over two hours watching for a button that had never been made. Three things now stand in the way, weakest last: agent._verify_confirmation_claims appends a visible correction to any reply that announces one while confirm.current() is empty; the prompt states on every turn whether something is parked, with the action and the real time left, so the honest answer is available; and a hard rule says not to announce one at all. None of them makes the sentence impossible — a model can assert anything, and a page claiming otherwise would be the same error one level up. What changed is that the false version now corrects itself in the same message instead of costing you an evening.

Why we chose this

Why matching on the words is acceptable here and almost nowhere else. The confirmation prompt is sent by the harness, not written by the model: when a call parks something, bot.py renders confirm.describe(parked) with the Approve/Deny buttons as its own message, immediately after the reply. So a sentence pointing you at a pending confirmation is redundant when it is true and load-bearing only when it is false — there is no case where correcting it costs you information. The existence check runs first and is exact; only the wording match can be wrong, and it can only be wrong about whether a sentence claimed something, never about whether a preview exists. That is the opposite balance to the sibling check on invented downloads/ paths, where a false alarm would brand a real save a lie — which is why that one is deliberately forgiving and this one is not.

The model cannot confirm its own actions — structurally. A tier-3 tool call returns a preview and halts the tool chain. Your "yes" is matched by code in on_message before the agent is ever invoked, and fires the parked action directly. The approval path never passes through the model, so no message content anywhere — no channel text, no web page, no clever phrasing — can talk its way into a delete. Ambiguity is not consent.

Why deny rules run before confirm rules: a refused action must never come back asking to be approved. If the guild isn't allowlisted, no confirmation is on offer — otherwise "just say yes" becomes a social-engineering surface pointed at you.

Why force doesn't exist in policy.py: policy says what a call needs; whether that need was met is the caller's bookkeeping. A "the confirmation already happened" flag inside policy would be a second answer to the same question — and a lie waiting to be passed.

Guests get neither half of a confirmation. On the guest lane, anything that would confirm is a flat deny — a guest must not receive the preview (it leaks what would happen) and must not generate approval traffic at you. The registry refuses to even register a guest-reachable capability that could confirm; a policy rule re-states it anyway. Twice, as always.

Paper trail

Dry-runs and confirmations print in full in the CLI / DM; parked and fired confirmations log in the bot log; benham.py usage counts proposed vs confirmed. Sample dry-run output: CLI → do.py.

A preview that really happened leaves a PROPOSED line, so "was there ever a confirmation here?" is answerable from the log rather than from anyone's recollection — that is how the 2026-08-17 pair was established. A reply that announced one without a call behind it logs agent: reply claimed a pending confirmation with nothing parked, with the offending sentence quoted. A run of those means the wording match has drifted or the model is fighting the rule, and either is worth knowing. Checks: tests/test_claims.py.
